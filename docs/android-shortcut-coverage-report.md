# Crawl 快捷键与 Android 紧凑交互覆盖技术报告

## 1. 摘要

**用户指出的单回合等待缺口成立，而且存在标签与行为不一致。** 当前紧凑键盘中心显示“等待 / Wait”（资源名为 `keyboard_rest`），却发送数字盘 `5`、执行自动休息 `CMD_REST`；真正的原地等待一个玩家回合是 `CMD_WAIT`，默认键为 `.` / `s` 等。二者不能互相替代。当前游戏命令抽屉没有独立等待按钮；点玩家自身格仅在没有物品、没有上下楼动作等条件下才会等待，不能作为稳定的战术等待入口。

更大的问题不是“Android 没有移动适配”，而是**游戏主状态的高频动作覆盖较窄，菜单与描述页已覆盖的功能又缺少稳定、短路径的入口**。现有实现已经有八方向键、探索、自动战斗、背包、拾取、六槽情境行、游戏命令抽屉、状态详情、快捷法术/能力栏、地图长按查看和目标点选；不应重复建设这些机制。

建议实施顺序：

1. **先补独立单回合等待**，与自动休息并列；不要用长按休息、点击自身或重复宏替代。
2. **利用现有四行布局的游戏态空情境行补充高频动作**，优先饮用、阅读、射击/箭袋动作、施法；不继续压缩热区。
3. **扩展现有命令抽屉的功能覆盖与分组**，补搜索、跨层旅行、物品批量管理、盟友命令等；保留完整键盘作为兜底而不是主要入口。
4. **补地图与瞄准的高级操作**，但严格区分普通确认、终点确认和强制操作。
5. 最后考虑 PocketZot 式分页、自定义和修饰键，不以新控件配置系统作为等待键的前置条件。

本轮只交付分析文档，不改游戏、翻译资产、资源、设置或存档，不构建 APK、不操作设备、不提交或合并。

### 2.1 覆盖判定规则

| 等级 | 含义 | 可以证明什么／不能证明什么 |
|---|---|---|
| 直接 | 紧凑游戏态可见按钮 | 可以启动该命令；后续目标/物品选择仍可能需要操作 |
| 菜单 | 当前游戏命令抽屉有明确动作 | 不是每项都首屏可见；布局会按字体重排 |
| 情境 | 进入对应页面后，有实际有效的情境按钮 | 不证明进入该页面本身无需完整键盘 |
| 间接 | 点击物品/法术/地形/角色等，经多步可达到同一功能 | 不视为对应专用命令及所有变体均被覆盖 |
| 键盘 | 需要展开完整键盘或使用实体键盘 | 算兜底可达，不算紧凑交互完整 |
| 未证实／不适用 | 未确认完整触屏链路，或内部/平台专用动作 | 不从命令名称、按钮标签或枚举存在推断可用 |

必须特别区分：

- 查看命令帮助 ≠ 点击执行任意命令。
- 进入背包 ≠ 覆盖批量丢弃、按数量操作、武器快速切换等全部语义。
- 打开法术列表 ≠ 已覆盖 `z`、`Z`、普通射击、强制终点等所有施法/瞄准行为。
- `p` / `Shift-Tab` 的 `CMD_AUTOFIRE` ≠ 无默认键的 `CMD_AUTOFIGHT_NOMOVE`。
- `.` 在主游戏是等待，在瞄准中是终点确认，在大地图中是前往目标；不能把新等待键无条件带进所有页面。

## 3. 重点结论：等待与休息不是同一功能

### 3.1 当前中心键的完整链路

先核对显示文本而不是根据资源名猜测：`values/strings.xml:43` 是 `Wait`，`values-zh/strings.xml:43` 和 `values-zh-rCN/strings.xml:44` 是“等待”。`DCSSKeyboard.java:448–450` 在 GAME 中继续使用此资源，因此该不一致不仅存在于 XML 初始值，也存在于运行时上下文刷新。先前会话按资源名把它简称“休息键”，这里明确纠正可见标签。

```text
keyboard_mobile.xml:91–100
  key_mobile_5，资源 keyboard_rest（显示“等待 / Wait”），tag="149"
    → Android KEYCODE_NUMPAD_5
    → DCSSKeyboardBase.java:175–180 原生按下/抬起
    → SDL_androidkeyboard.c:192，SDL_SCANCODE_KP_5
    → windowmanager-sdl.cc:354，CK_NUMPAD_5
    → cmd-keys.h:31，CMD_REST
    → main.cc:2204，_do_rest()
```

`_do_rest()` 检查安全与休息条件，并进入 `RMODE_REST_DURATION`；已充分恢复时可以进入 `RMODE_WAIT_DURATION`。它是可持续多个回合、可被中断的自动流程，**不是“只跳过下一回合”**。报告不把它简化成固定等待某个回合数，也不保证任何条件下都恢复满生命/法力。

真正的单回合等待链路：

```text
. / s / CK_CLEAR / CK_NUMPAD_DECIMAL / CK_DELETE
    → CMD_WAIT
    → update_acrobat_status()
    → you.turn_is_over = true
```

这里的“一回合”是一次玩家行动，不意味着所有速度、状态下都等于固定现实时间或完全相同的游戏耗时。

额外数字方向盘 `keyboard_extra_numeric.xml:82–91` 也引用 `keyboard_rest` 并发送149。后续实施应明确只改紧凑GAME还是同步修正该消费者；不能改共享标签而不检查它。现有 `.claude/scripts/tests/test_android_quickbar.py:94` 还断言该英文资源为 `Wait`，未来测试必须同时核对命令语义与上下文，不只是字符串名字。

### 3.2 为什么已有操作不能替代

| 候选替代 | 不成立的原因 |
|---|---|
| 中心显示“等待”的按钮 | 名称看似正确但实际执行 `CMD_REST`，可能开始自动休息或长等待；危险条件下还可能拒绝 |
| 点玩家自身 | `tilereg-dgn.cc:494–525` 根据物品与地形优先拾取/上下楼；不是地形无关的等待 |
| 探索／自动战斗 | 会寻路、攻击或拒绝执行，不是原地等待 |
| 打开完整键盘按 `s` / `.` | 功能兜底存在，但破坏“紧凑键盘内完成基础战术操作”的目标 |
| 自定义宏 | 把基本动作缺口转嫁给用户，还引入宏/上下文配置负担 |

### 3.3 最小修复与推荐布局的取舍

- **最小兼容方案：**中心保留自动休息行为，但将显示文本明确为“休息”；在当前游戏态空闲的六槽行中增加真正的“等待”。无需新页面、不改变老用户中心键动作习惯。
- **推荐长期方案：**游戏态方向盘中心改为真正的 `CMD_WAIT`，使“等待”标签与行为一致；把“休息”放入右侧动作区或第四行，两者始终是不同按钮。它与 PocketZot 的中心 `.`、独立 `5` 更一致，也使方向盘语义完整：八个相邻位置加原地。
- 两方案都必须只对 GAME 生效；NAVIGATION/TEXT 的中心与确认行为单独保留。不能只全局替换 XML 的 `149` 为句点而不检查上下文切换。
- 不采用“短按等待、长按休息”作为唯一入口：长按查看已存在，重复按键也可能发生；隐含危险动作不利于可发现性和防误触。

## 4. 当前紧凑键盘与菜单到底覆盖了什么

### 4.1 固定键盘

当前紧凑布局前三行16个固定按钮及第四行情境槽为：

```text
↖  ↑       ↗    探索    自动战斗
←  等待(*) →    背包    拾取
↙  ↓       ↘    菜单  返回  展开
[槽0] [槽1] [槽2] [槽3] [槽4] [槽5]
(*) 可见“等待”，实际为REST。
```

- 八方向移动用真实方向键/数字盘键；不是仅在字母键上画箭头。
- 游戏态直接动作只有休息、探索、自动战斗、背包、拾取；菜单、返回、展开属于导航控件。
- 第四行已预留固定高度。默认游戏描述符没有动作，空槽不可点但继续占位；因此存在**不增加键盘高度即可补高频入口**的空间。
- 非游戏态探索位置变确认，战斗、背包、拾取、菜单隐藏但不重排；中心显示为 `5`。
- TEXT 自动显示完整键盘；用户手动展开后优先保留完整布局，不被自动上下文覆盖。
- mode 4 约束至少 48dp 行高，compact/full 都占四行。该约束不等于在所有屏宽和字体下所有横向热区都已通过人体工学验收。

### 4.2 游戏命令抽屉

`commands[]` 当前固定有 15 个槽位：

| 分组（本报告归类，不是当前已有标签页） | 当前入口 |
|---|---|
| 主循环 | 探索、背包、拾取、当前位置出口 |
| 战术观察 | Full View（视野内容列表）、地图 |
| 角色管理 | 法术列表、能力、记忆法术、角色概览、技能、信仰、变异、已知物品 |
| 帮助 | Commands（命令帮助） |

注意：

- “Exit”是当前位置楼梯/门/商店等**地形出口**槽，不是“保存并退出游戏”。无出口时灰显并解释原因；祭坛不按普通出口处理。
- `Full View` 是 `CMD_FULL_VIEW`，不是屏幕全屏开关，也不等于 `x` 光标查看模式。
- 原生 `GameMenu` 与 Android 抽屉不同：紧凑 F1 在 GAME 被拦截为 Android 抽屉，完整键盘 `~` 才进入原生菜单，其保存、宏等条目不能算紧凑F1已经直达（`main.cc:2080–2117`、`tilesdl.cc:718–732`）。
- 抽屉还有动态 Quick Cast / Quick Abilities，能显示名称、费用、不可用原因、长按描述；不是只有上表 15 项。
- 抽屉已有字体驱动重排、滚动、固定不可用槽和防穿透遮罩。可以扩展这些现成机制，无需重写菜单框架。

### 4.3 已有情境行的边界

| 页面 | 当前已接入的主要动作 | 仍需注意 |
|---|---|---|
| 背包／拾取／已知物品 | 确认、返回、前后分类、多选、模式切换等，依实际 flags 提供 | 进入特定批量操作模式是否有入口要另外审计 |
| 物品描述 | 返回及当前物品候选动作中的部分使用/装备操作 | 四个业务槽可能溢出；不能证明铭刻、改字母等后排动作都可见 |
| 法术描述 | 当前情境行只有返回（`describe.cc:5085–5087`） | 施法需依赖快捷栏、其他入口或键盘；不能把描述页有文字提示当作存在施法按钮 |
| 瞄准 | 确认、取消、前目标、后目标、自身 | 高级路径/强制/终点/对象循环不是同一批动作 |
| 确认／更多 | 是、否、总是（适用时）、继续 | 不能泄漏底层游戏态快捷键 |
| 大地图 | 返回、上下楼梯、传送门、陷阱 | 排除区域、路径点、跨层浏览等仍需额外入口 |
| 使用物品列表 | 模式、描述、列表切换、徒手等 | 页内支持 ≠ 主游戏有饮用/阅读/激活专用入口 |
| 商店 | 购买/查看、排序、购物清单 | 大写字母/修饰点按等特殊选择仍须单独检查 |
| 通用菜单／描述／神祇／地形 | 视图、过滤、更多信息、加入、上下楼、目的地、开关门等 | 按实际页面可用键生成；不能把游戏 `C/O` 与地形局部 `c/o` 混用 |
| 技能 | 视图、全部技能、训练目标等情境动作 | 当前实现应以源码而非旧计划表为准 |
| 跨层旅行 | 默认目标、路径点、祭坛、帮助等 | 打开旅行提示本身不一定有紧凑入口 |
| 显示图层／箭袋动作 | 对应分层和选择模式 | 有子页面不等于已有稳定主入口 |

### 4.4 完整键盘与情境行使用不同输入路径

这里存在必须在实施前识别的技术限制：

1. **完整 Ctrl 键盘有源码支持。** `keyboard_ctrl.xml` 的组合 tag 经 `DCSSKeyboardBase.java:116–142` 发送 Ctrl down、字母 down/up、Ctrl up；SDL 路径识别 modifier。不能照搬旧说明，把 Android 全部 Ctrl 功能判为不可用。
2. **六槽 `sendContextKey()` 的覆盖较窄。** Java 当前只明确接收 Enter/Esc/Tab、可打印 ASCII，负值 CK 键则转交原生桥；直接填 `CONTROL('F')`（6）或 `CONTROL('S')`（19）会被该路径遗漏。原生桥 `syscalls.cc:415–435` 还只白名单放行 `CK_LEFT/CK_RIGHT`，所以不能把“Java 接收负值”理解为全部 CK 特殊键都可用。
3. 因而，“给情境按钮加一个搜索/排序标签”不等于功能完成。要么从现有 C++ 抽屉以命令启动主游戏搜索，要么为局部 Ctrl 快捷键最小扩展发送路径并验证键值；不能用发送普通字母 `f/s` 代替。
4. 本轮是源码链路确认，未实际点击 Ctrl 组合键进行真机验收。

### 4.5 缺失与部分覆盖项目：按影响排序

这里的 P0/P1/P2 是本报告建议的实施优先级，不是已经登记的缺陷严重性，也不代表本轮发现了崩溃或输入回归。默认按键均以附录与 `cmd-keys.h` 为准。

本表前两列状态保留冻结基线；最右列记录 P1–P3 候选实现，不能解读为全部已合并。设备证据和未完成门槛见 [P3 验证记录](android-shortcut-p3-verification.md)。

### 4.6 不仅缺入口，还存在“已有页面放不下动作”

这是六槽机制的容量问题，不应与“尚未接入情境键盘”混为一谈：

| 页面 | 源码规则 | 可确认的风险 |
|---|---|---|
| 物品描述 | `describe.cc:4300–4328`，槽 2–5 优先放直接使用，元数据动作靠后 | 铭刻、调整、箭袋或技能目标依物品组合可能不显示 |
| 使用物品 | `item-use.cc:793–816`，装备切换、模式、徒手、列表、描述按条件进入四槽 | 五种候选同时满足时，末项可能没有位置 |
| 技能 | `skill-menu.cc:1142–1177`，目标、视图、清目标、模式、全部、帮助按条件取前四个 | 不等于菜单内部的模式/开关行完全不可点，但情境栏不是完整集合 |
| 箭袋选择 | `quiver.cc:2764–2779`，固定聚焦模式，后三槽按物品/法术/能力/清空排序 | 三类都存在时，清空 `-`无法进入最后三个槽 |
| 快捷法术/能力行 | `tilesdl.cc:1299–1349`，一行截断；951–1019按视野预算隐藏 | 底部看不见不等于没有法术；完整抽屉可用，但需要明确“更多”提示 |

可采用的最小原则是：**默认行展示常用动作，溢出时有明确可达的完整动作列表；不依赖用户猜测展开键盘。** 优先复用当前菜单/描述的真实动作列表和现成弹窗，不为每个页面设计一种不同的翻页手势。是否增加统一“更多”机制，应以这些已确认截断点为范围单独实施，不能顺带扩成通用 UI 框架迁移。

- 默认控件代码冻结在公开仓库提交 `2fc224ef10fa95271ad36f10ab6b8caf7805a07a`，提交时间 2026-09-01。公开源码与线上部署可能不同步，不能声称该代码就是当前网站的逐字构建输入。
- 具体对照引用 [control-sets.ts](https://github.com/pocketzot/pocketzot/blob/2fc224ef10fa95271ad36f10ab6b8caf7805a07a/src/game/input/control-sets.ts)、[touch.ts](https://github.com/pocketzot/pocketzot/blob/2fc224ef10fa95271ad36f10ab6b8caf7805a07a/src/game/input/touch.ts)、[game-view.ts](https://github.com/pocketzot/pocketzot/blob/2fc224ef10fa95271ad36f10ab6b8caf7805a07a/src/views/game-view.ts)。没有登录服务器或实际发出游戏行动。

### 5.2 默认控制集的完整三页布局

除固定方向盘、Esc、Enter、Shift、Ctrl、完整键盘入口外，Standard 集有三页，每页 3 行 × 4 列：

| 页 | 第一行 | 第二行 | 第三行 |
|---|---|---|---|
| `@` micro，即时操作 | `Tab`、`5`、`i`、`o` | `q`、`r`、`f`、`v` | `a`、`'`、`x`、`,` |
| `>` macro，探索/管理 | `w`、`R`、`t`、`P` | `d`、`Ctrl-F`、`G`、`Ctrl-O` | `X`、`e`、`<`、`>` |
| `?` info，信息 | `@`、`%`、`^`、`=` | `A`、`m`、`}`、`\` | `$`、`M`、`I`、`?` |

最相关的差别：

- 方向盘中心发 `.`，而 micro 页另放 `5`；**单回合等待和自动休息同时存在**。
- `q/r/f/v/'/x` 与探索、战斗、背包并列；不要求每次从背包或角色描述页绕行。
- 搜索 `Ctrl-F`、旅行 `G`、大地牢概览 `Ctrl-O`、丢弃 `d` 都有控制页入口。
- Shift 方向是跑动，Ctrl 方向是定向不移动攻击相关键；不增加八个永久方向按钮即可表达更多模式。
- `z` 不在该版本 Standard 的 36 格内；它已有快捷法术行。不能据旧宣传截图把默认 `z` 位置当成当前源码事实。

### 5.3 值得借鉴，但不应照搬的设计

| PocketZot 机制 | 对 Android 的启示 | 不应照搬的部分 |
|---|---|---|
| 战斗/探索/信息三页 | 将有限空间留给常用动作，低频命令可预测地收纳 | 不为补一个等待键引入三页和持久配置；不照搬对新手不透明的单字符标题 |
| 中心等待、独立休息 | 基础战术动作不应隐藏在字母键盘里 | 中心句点在不同模式含义不同；必须与当前上下文绑定 |
| 固定方向盘 + Shift/Ctrl | 后续可提供跑动／原地攻击模式 | 明确模式提示、单次复位；不要静默保留危险 Ctrl/Shift 状态 |
| 可编辑按键、短宏、Ctrl/F 键、导入导出 | 熟练玩家最终可定制自己的高频入口 | 自定义不应替代好用默认值；宏可能跨上下文，不宜初期实现通用宏配置层 |
| 页内专用控件、列表内可点动作 | 列表的模式/排序/确认应跟随实际上下文 | 不在原生端解析英文提示来猜按钮，应复用现有 C++ 描述符 |
| 怪物浮层与直接查看 | 让当前视野中的对象更容易触达 | Android 已有 Full View 及底层 MonsterRegion，应先复用；避免列表普通点击直接攻击 |
| 按压反馈、后台停止重复、滚动防误触 | 把生命期和手势取消当成输入正确性的一部分 | PocketZot 的方向盘（含中心）支持按住重复，不适合作为“一个点击只等待一个回合”的无条件默认 |

PocketZot 本身也不是所有命令均有专用按钮：高级大地图操作、宏录制等仍有键盘/协议边界。它提供的是良好的分层样例，而不是可直接照抄的“全覆盖标准答案”。

## 6. 建议设计：先利用现有空间，再做分层

### 6.1 第一阶段：不增高、不加配置系统

推荐原型（最终按钮顺序需要真人测试，不是本轮已实施布局）：

```text
↖  ↑    ↗    探索    自动战斗
←  等待 →    背包    拾取
↙  ↓    ↘    菜单  返回  展开
休息  饮用  阅读  射击  施法  能力
```

设计约束：

- 仍是固定四行，复用六槽情境行；中心仅 GAME 改为等待。
- 等待、休息绝不共用模糊“停留”标签；可访问性描述说明单回合／自动休息差异。
- “射击”实际对应当前箭袋动作，不应误导玩家认为它永远是投掷实体弹药；正式短标签在实施时按术语流程确认。
- 进入背包、目标、确认、文本输入后，第四行继续由当前最内层上下文接管；不能同时显示底层饮用/施法等动作。
- 无法施法/使用能力时保留位置并明确不可用原因，或先用现有命令自己的无可用动作反馈；不要让图标重排，也不要在 Java 复制游戏规则。
- 若 6 格在窄屏/大字体下不满足热区与文字可读性，先减可见项并提供“更多”入口，不增加第五行或缩小字号来硬塞。
- 如果要最大化旧习惯兼容，先采用第 3.3 节的“保留中心休息、第四行补等待”版本；两方案应在实施前选定，不能混用验收结论。

### 6.2 第二阶段：扩展现有抽屉，而不是第二套菜单

将当前命令网格按明确标题分组；是否需要标签页取决于新增后的实际滚动成本，先复用已有滚动网格。

- **战斗与物品：**射击/箭袋、饮用、阅读、激活、武器切换、丢弃、喊叫/盟友命令、定向关门。
- **探索与地图：**搜索、跨层旅行、地牢概览、地图排除/路径点入口、自动拾取开关。
- **角色与信息：**现有角色、技能、法术、能力等，加消息历史、金币/购物清单、符文、笔记/层注释等低频入口。
- **系统与高级：**保存退出、重复操作、宏与键位帮助；放弃角色必须显著区别并保留原确认。

此处是候选分组，不要求一次性把所有底层 `CMD_*` 显示为按钮。无默认键命令按实际玩家价值个别评估，例如 `CMD_AUTOFIGHT_NOMOVE` 值得显式纳入；不能因缺默认键而一概排除，也不能自动将内部鼠标事件、调试命令、终端暂停等混入普通动作目录。

### 6.3 第三阶段：上下文高级动作与轻量定制

- 大地图提供明确的“更多地图操作”，容纳排除/清除排除/半径、路径点、上下层、查找祭坛或物品等；先复用现有命令语义。
- 瞄准提供“高级”入口，区分正常确认、终点确认、强制确认、切换箭袋/动作、路径显示；危险动作不抢占默认确认槽。
- 如仍有稳定的角色流派差异，再提供少量可选高频键或预设。优先固定动作选择，不先支持任意跨页面宏。
- 新持久配置、通用 action schema 或新模块需要单独设计决策；本报告不将其作为第一阶段要求。

## 7. 实施边界与验证建议

### 7.1 复用点

| 改动 | 优先修改现有机制 | 约束 |
|---|---|---|
| 游戏态补动作 | `ui::input_descriptor()`、现有 `InputDescriptor`、Java 六槽显示 | 当前 `InputActionScope` 会发布 NAVIGATION；不能简单给主游戏套一个 scope 就假定仍是 GAME |
| 中心等待/休息分离 | `keyboard_mobile.xml` 与 `DCSSKeyboard.setInputContext()` | 不做所有上下文共享的静态 tag 替换；标签、tag、实际输出同步 |
| 抽屉补命令 | `topbar-drawer.cc` 的命令网格及原命令执行返回路径 | 避免用字母串宏代替已有 C++ 命令；不从 Java UI 线程直接操作游戏状态 |
| Ctrl 情境操作 | `DCSSKeyboardBase.sendContextKey()` 与既有 SDL 输入桥 | 先测试控制字符、Enter/Tab/Esc 与特殊 CK 键，再接页面；防按下未抬起 |
| 快捷栏更多 | `tilesdl.cc` 与现有 Quick Cast/Quick Abilities | 当前溢出截断、短窗口隐藏；先给完整列表入口，不重建法术/能力数据模型 |
| 列表与遮罩 | `CommandGrid`、`QuickButton`、`DrawerScroller`、现有 UI Scroller | 保留空槽几何、嵌套返回、取消拖动和防穿透 |

新增触屏动作的正确性以原命令规则为准：不绕过法力、射程、失败率、物品数量、铭刻警告、危险确认和回合消耗；不要在客户端复制这些判断。

### 7.2 功能验收矩阵

以下是后续实施应执行的测试，不是本轮已经完成的测试。

| 场景 | 验收点 |
|---|---|
| 正常空地等待 | 单击仅产生一次 `CMD_WAIT`，坐标不变、玩家回合数增加一次，无自动休息状态 |
| 有敌人、满/不满生命法力 | 等待不退化成安全休息判断；仍按原游戏规则消耗一次行动 |
| 玩家脚下有物品、楼梯、商店、祭坛 | 等待按钮仍只等待；不拾取、不换层、不进入或祈祷 |
| 自动休息 | 独立按钮仍进入原 `CMD_REST` 流程，可由原有条件中断 |
| 连续点击与按住 | 初版等待单次触发；不会同时收到 down/click 两次动作，不把长按暗中变成长等待 |
| 瞄准／查看／大地图 | 切换后没有主游戏等待泄漏；普通确认、终点确认、强制确认行为分别校验 |
| 饮用／阅读／施法／能力 | 有/无可用条目、数量、警告、取消、确认、目标选择完整通过；零额外回合 |
| Ctrl 搜索／局部排序 | 真正点击按钮，经 Java/SDL/native 链确认收到正确控制键；不能用 ADB 等价硬件键代替触屏测试 |
| 背包批量管理 | 分类、多选、数量、确认/取消、查看描述后恢复选择与滚动位置 |

## 8. 结论

紧凑键盘目前最需要补的是**单回合等待与高频动作的直接入口**，其次才是“更多功能键”。PocketZot 的参考价值在于：方向盘覆盖原地动作、休息独立、操作按战斗/探索/信息分层、用页面专属控件表达当前可用命令。

技术上应先复用当前空闲游戏态情境行、原生命令抽屉和输入描述符；对于搜索、地图管理、强制操作等，先查清入口、输入通道和上下文，再逐项补齐。**不能把完整键盘存在当作触屏覆盖完整，也不能把所有键都塞进主屏当作优化完成。**
